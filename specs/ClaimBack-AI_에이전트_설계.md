## 1. 설계 원칙

1. **진행은 규칙 기반 코디네이터가 맡습니다.** 에이전트끼리 자유롭게 대화하지 않고, 정해진 입력을 받아 정해진 형식(JSON 스키마)으로만 결과를 냅니다. 같은 입력이면 같은 순서로 실행되므로 테스트와 데모가 안정적입니다.
2. **판단이 필요한 일만 AI 에이전트(Meta 모델)가 맡습니다.** 계산, 검증, 편철은 규칙 기반 담당이 맡습니다. 검증은 에이전트가 손댈 수 없는 바깥에서 돕니다.
3. **페르소나는 말투 설정이 아니라 업무 헌장입니다.** 각 프롬프트에는 역할, 할 일, 하지 않을 일, 출력 스키마, 불확실할 때의 처리(보이지 않으면 null과 이유)만 짧게 담습니다.
4. **숫자와 이름은 AI가 직접 쓰지 않습니다.** 문안 작성 담당은 `{{principal}}` 같은 값 슬롯, `{{quote:EX1:item3}}` 같은 인용 슬롯, `[[EX:1]]` 같은 증거 태그만 씁니다. 실제 값과 원문은 편철 담당이 사용자 확인값으로 바꿔 넣습니다. 환각 차단을 사후 검사에만 맡기지 않고 구조로 막습니다.
5. **사용자가 최종 결정권자입니다.** 체크포인트 2곳(사실·가림 확인, 최종 서류 확인)을 통과해야 다음 단계로 갑니다. 초안 문장도 사용자가 문장별로 수정·승인합니다.
6. **법적 평가를 하지 않습니다.** 승소 가능성, 청구 가능 여부, 발화의 법적 성격(예: 채무 승인 여부)을 판단하지 않습니다. AI는 사실을 읽고 분류하며, 무엇을 강조할지는 사용자가 고릅니다.
7. **명칭 규칙.** 에이전트 이름, 제품 설명, 서류 작성자 표시 등 **자기 지칭**에 "변호사", "법률사무소", "법무사", "paralegal", "legal assistant", "attorney", "lawyer"를 쓰지 않습니다. 고지·안내 문구(예: "법률 상담은 변호사에게 받으세요")는 문구 ID 단위 허용 목록(`DISCLAIMER_KO`, `DISCLAIMER_EN` 등)으로만 허용합니다.
   - 변호사법 제112조 제3호: 변호사가 아니면서 변호사나 법률사무소를 표시·기재하는 행위 처벌
   - 법무사법 제3조 제2항: 법무사가 아닌 자의 법무사 또는 비슷한 명칭 사용 금지
   - 캘리포니아 Bus. & Prof. Code §6452: 자격 없이 paralegal로 표시하는 행위 금지(§6454에 따라 legal assistant도 같은 뜻)
8. **모든 실행은 감사 로그에 남깁니다.** 에이전트, 모델 ID, 프롬프트 버전, 입력 해시, 소요 시간, 토큰, 비용.
9. **정답 데이터는 에이전트 입력에 넣지 않습니다.** 골든셋 정답 JSON은 테스트만 읽습니다.

## 2. 구성

### 2-1. 실행 흐름

```text
[코디네이터: 규칙 기반 상태 기계]

1. 접수 담당 (규칙)                 해시, 호증 번호, 영상 프레임 추출(중복 제거)
2. 판독 담당 (Spark)                증거별 병렬 판독
   ∥ 시각 감식 담당-1 (SAM 3.1)     명사구(signature, stamp, chat bubble, face)로 분할
3. 사실 정리 담당 (Spark)           증거 간 사실 병합, 충돌 표시, 질문, 발화 사실 유형
   ∥ 시각 감식 담당-2 (SAM 3.1)     판독 박스(말풍선, 글자 개인정보)로 위치 보정
4. 개인정보 보호 담당 (규칙)        가림 계획
   ◆ 체크포인트 1 (사용자): 사실값 확정, 강조 발화 선택, 채무자 주소·제출 법원, 가림 확인
5. 시각 감식 담당 (SAM 3.1, P1)     고른 말풍선 영상 추적, 스틸컷
6. 계산 담당 (규칙)                 G2 요건 칸 결손, G4 한도, G5 이자(충당, 기산일)
7. 문안 작성 담당 (Spark) ⇄ 검증 담당 (규칙)      슬롯 문안, G1a·G3, 최대 2회 수정
   → 사용자 문장별 수정·승인 (수정 문장은 G1a·G3 재검사)
8. 타임라인 담당 (Muse Image, P1) ⇄ 검증 담당     글자 없는 삽화, G7, 실패 시 SVG만
9. 편철 담당 (규칙)                 슬롯 치환, 정형 문구, KR·US 서류
10. 검증 담당 + 개인정보 보호 담당  G1b 최종 값 대조, 누출 검사(규칙), G6 Spark 재판독(P1)
   ◆ 체크포인트 2 (사용자): 최종 서류 확인
```

v1과 달라진 순서: 감식을 판독 전후 두 단계로 나눴고(판독 박스가 있어야 보정 가능), G2를 초안 전으로 옮겼고, 최종 개인정보 검사를 편철 뒤로 옮겼습니다(완성된 서류를 검사해야 하므로).

## 3. 담당별 명세

### 3-1. 판독 담당 (Reader)
- 페르소나: 보이는 것만 그대로 옮겨 적는 기록원. 추측하지 않고, 안 보이면 비워 둔다.
- 책임: 이미지와 영상에서 발화(말풍선 단위), 금액, 날짜, 당사자 표시, 식별번호(계좌번호, 주민번호)를 원문 그대로 읽고 위치 박스와 함께 반환합니다.
- 모델: `muse-spark-1.3`, reasoning low~medium. M0에서 `muse-spark-1.1`, `1.2`와 속도·정확도를 비교해 정합니다.
- 입력: `evidence_id`, 이미지. 영상은 M0 결과에 따라 (가) 영상을 Spark에 직접 입력하거나 (나) 접수 담당이 중복 제거한 핵심 프레임 묶음과 타임스탬프를 넣습니다.
- 좌표: 모델이 내는 좌표 형식(픽셀 또는 0~1000 정규화)을 M0에서 확인하고, 저장할 때는 항상 원본 이미지 픽셀 좌표로 바꿉니다.
- 출력: `Reading { evidence_id, items[ { item_id, kind, text_verbatim, normalized, box[x1,y1,x2,y2], frame_ts, speaker, confidence } ] }`
- 금지: 의미 해석과 법적 평가, 원문에 없는 값 생성, 정규화값을 원문처럼 표시
- 실패 처리: 스키마 오류면 오류 내용을 붙여 1회 재요청, 다시 실패하면 해당 증거 HOLD
- 테스트: 골든셋 금액·날짜 일치율 95% 이상, 박스와 정답 영역 IoU 0.3 이상, 금지 표현 0건

### 3-2. 시각 감식 담당 (Vision Analyst)
- 페르소나: 증거가 되는 물체만 정확히 오려 내는 감식 담당.
- 모델: `sam-3.1` (Responses API + Files API). 출력 파싱은 `meta-sam-parser`.
- 감식-1 (판독과 병렬): 명사구("signature", "red stamp", "chat bubble", "face")로 서명·도장·말풍선·얼굴 마스크를 만듭니다.
- 감식-2 (판독 이후): 판독 담당이 준 박스로 말풍선과 글자 개인정보의 위치를 보정합니다.
- 영상 추적 (P1, 체크포인트 1 이후): 사용자가 고른 말풍선을 프레임마다 추적해 가장 잘 보이는 프레임을 고릅니다.
- 입력: `evidence_id`, 대상 목록(명사구 또는 박스), 영상이면 프레임 범위
- 출력: `Segments { evidence_id, objects[ { target, source: noun|box, box, mask_ref, frame_range, score } ] }`
- 금지: 원본 수정(가공은 사본에만)
- 실패 처리: 명사구로 안 잡히면 박스 프롬프트로 1회 재시도, 그래도 없으면 "미검출"로 기록하고 진행
- 테스트: 차용증 서명·도장 IoU 0.5 이상, `meta-sam-parser` 파싱 계약 테스트, 추적 스틸컷이 대상 전체를 포함

### 3-3. 개인정보 보호 담당 (Privacy Guard)
- 페르소나: 애매하면 일단 가리고 사용자에게 묻는 보수적인 보안 담당.
- 책임:
  - 가림 계획: 판독 결과의 식별번호(정규식으로 판별), 얼굴과 프로필 사진(감식-1), 사건과 무관한 제3자 정보
  - 정책: 계좌번호는 끝 4자리 유지, 주민번호 뒷자리와 SSN은 가림, 무관한 제3자 정보는 전부 가림. 글자 박스에는 여백을 더합니다(기본: 박스 높이의 20%, 최소 4px).
  - 가림 적용: 이미지 픽셀을 바꾼 사본을 만듭니다. PDF 위에 주석이나 도형만 얹는 방식은 쓰지 않습니다.
  - 최종 검사(P0, 규칙): 편철된 PDF에서 이미지를 뽑아 가림 영역 픽셀을 확인하고, PDF 텍스트와 메타데이터에 전체 주민번호·계좌번호가 없는지 정규식으로 검사합니다.
  - 최종 검사(P1, G6): 편철된 PDF를 Spark에 그대로 넣어 다시 판독하고, 전체 번호가 보이면 차단합니다.
- 모델: 규칙 + `sam-3.1`(얼굴) + `muse-spark-1.3`(G6)
- 출력: `RedactionPlan { evidence_id, regions[ { box | mask_ref, reason, policy_rule, keep_last4, padding_px } ] }`, `PrivacyCheck { status, method: rule|reread, leaks[] }`
- 금지: 증명 대상(송금 금액, 날짜, 당사자 이름)을 가리는 것
- 테스트: 가린 픽셀 전부 검정, 여백 적용, 원본 불변, 끝 4자리 유지, PDF 텍스트·메타데이터 전체 번호 0건, 재판독(P1)에서 전체 번호가 보이면 차단

### 3-4. 사실 정리 담당 (Fact Organizer)
- 페르소나: 흩어진 기록을 날짜순으로 맞추고 서로 안 맞는 곳을 짚어 주는 정리 담당. 결론은 내리지 않는다.
- 책임:
  - 증거별 판독 결과를 `LoanFactDraft`(당사자, 대여일, 원금, 변제기, 이자 약정, 일부 변제, 독촉)와 시간순 이벤트로 병합합니다.
  - 값이 충돌하면 표시하고, 사용자에게 물을 질문을 만듭니다(예: 채무자 주소가 없음, 두 증거의 금액이 다름).
  - 발화마다 사실 유형을 붙입니다: `loan_request`(빌려 달라는 요청), `amount_mention`(금액 언급), `repay_promise`(갚겠다는 약속, 날짜가 있으면 함께), `reminder`(독촉), `other`.
  - 모든 값에 근거(`evidence_id`, `item_id`)를 연결합니다.
- 모델: `muse-spark-1.3`, reasoning medium
- 출력: `FactCandidates { draft, events[], conflicts[], questions[], utterances[ { evidence_id, item_id, tags[] } ], citations[] }`
- 금지: 청구 가능 여부, 승소 가능성, 권리 판단. "채무 인정", "채무 승인", "시효" 같은 법적 성격 표현. 근거 없는 값 채우기
- 테스트: 금액이 서로 다른 증거 2개를 넣으면 충돌로 표시, 모든 값에 근거 연결, 상환 약속 발화에 `repay_promise` 태그, 금지 표현 0건

### 3-5. 계산 담당 (Calculator, 규칙)
- 책임:
  - 한국: 일부 변제 충당(비용 → 이자·지연손해금 → 원본, 민법 제479조), 충당 후 남은 원금, 지연손해금 기산일, 청구취지에 넣을 이율 구간 문구(송달일까지 연 5%·6%·약정 이율, 그 다음 날부터 연 12%), 한도(G4)
  - 캘리포니아: 위반일 이후 연 10% 단리(Civil Code §3289, 약정 이율이 없을 때), 한도(G4)
  - 참고값: 사용자가 정한 기준일까지의 예상 총액(화면 표시용, 기준일을 함께 표시)
  - 요건 칸 결손(G2): 이체 내역, 변제기 근거, 당사자 신원 등 양식 칸을 채울 근거가 없으면 HOLD와 빈 칸 목록을 냅니다.
- 계산 규칙: `Decimal`, 원 미만 버림, 지연손해금은 변제기 다음 날부터 변제일 당일까지 포함, 1년 365일 고정(윤년 처리는 M1에서 근거 확인 후 고정), 약정 이율이 법정이율보다 높으면 지연손해금도 약정 이율(민법 제397조), 이자제한법 상한(연 20%) 초과 약정은 경고와 함께 상한으로 계산, 상사채권 여부는 사용자 선택값
- 출력: `Calculation { allocations[], remaining_principal, accrual_start_date, rate_clause_slots, reference_total { as_of, amount }, limit_check, missing_fields[] }`
- 테스트: 계획서 1-2(8) 고정 예시(지연손해금 14,383원, 남은 원금 4,014,383원, 기산일 2026-05-02)와 4-6절 계산기 케이스

### 3-6. 문안 작성 담당 (Drafter)
- 페르소나: 확인된 사실만 정해진 문안 틀에 옮겨 적는 작성 담당. 숫자와 이름은 직접 쓰지 않고 슬롯을 쓴다.
- 책임: 청구원인(한국어, P0)과 Statement of facts(영어, P1)의 사실 문장 초안. 청구취지와 시작·맺음 정형 문구는 이 담당이 쓰지 않고 편철 담당이 만듭니다.
- 문장 유형:
  - `fact`: 증거로 뒷받침되는 사실. `[[EX:n]]` 1개 이상 필수
  - `user`: 증거가 아니라 사용자 진술로 뒷받침되는 사실(예: 아직 갚지 않음). `[[USER]]` 태그
- 슬롯:
  - 값 슬롯: `{{principal}}`, `{{loan_date}}`, `{{creditor_name}}` 등 확인된 사실의 슬롯 목록 안에서만
  - 인용 슬롯: `{{quote:EX1:item3}}`. 말풍선 원문을 인용할 때 씁니다. 원문에 날짜나 금액이 있어도 슬롯 하나로 넣습니다.
- 모델: `muse-spark-1.3`. reasoning은 medium과 high를 M5에서 수정 루프 횟수와 지연으로 비교해 정합니다.
- 입력: 확인된 사실의 슬롯 목록(이름과 설명), 이벤트 순서, 사용자가 고른 강조 발화, 증거 목록, 문안 틀
- 출력: `SlotDraft { lang, sentences[ { sentence_id, type: fact|user, text_with_slots, ex_refs[] } ] }`
- 금지: 슬롯 밖 숫자(아라비아 숫자, 한글 수사), 날짜와 상대 날짜("다음 달", "열흘 뒤"), 당사자 이름·성·호칭, 법적 평가와 결과 예측("승소", "명백한 불법", "채무를 인정", "you will win" 등), 확인되지 않은 사실 추가, 정형 문구
- 수정 루프: 검증 담당의 지적 목록(`sentence_id` 포함)을 받아 최대 2회 수정, 그래도 실패하면 HOLD로 사용자에게 표시
- 사용자 수정: 사용자가 문장을 고치면 같은 검사(G1a, G3)를 다시 통과해야 합니다.
- 공개 배포 전 검토: 사건 유형별 고정 문장 틀을 기본으로 하고 AI는 순서 배열과 연결 표현만 맡는 방식(계획서 1-1(2))
- 테스트: 슬롯 밖 리터럴 0개, `fact` 문장 인용 누락 0개, 금지 표현 0건(정규식 목록)

### 3-7. 검증 담당 (Verifier, 규칙)
- 책임:
  - **G1a 슬롯 무결성** (초안): 슬롯 밖 아라비아 숫자, 한글 수사("오백만", "5백만", "삼십일"), 날짜 표현과 상대 날짜("4월 10일", "다음 달", "지난주", "열흘 뒤"), 기준값 당사자 이름의 전체·부분 일치(성, 이름, 호칭 "김 씨"), 존재하지 않는 슬롯 이름, 정형 문구를 검출
  - **G1b 최종 값 대조** (편철 후): PDF에서 텍스트를 뽑아 금액, 날짜, 이름, 법원명이 기준값·계산값과 일치하는지 확인
  - G3 문장별 근거: `fact` 문장의 인용 누락, 존재하지 않는 호증 번호 거부. `user` 문장은 `[[USER]]` 태그 확인
  - G7 타임라인 그림 검사: 판독 담당에게 그림 판독을 맡기고, 글자나 숫자가 보이면 실패(기본). 시연용 숫자 그림 모드에서는 기준값과 비교
- G2와 G4·G5는 계산 담당이 냅니다. 결과 문구는 양식 칸 기준으로 씁니다("이 양식의 다음 칸을 채울 근거가 없습니다: …").
- 출력: `GateResult { gate, status, findings[ { sentence_id | field, message, fix_hint } ] }`
- 테스트: G1a 변조 100건(유형별 고르게) 100% 차단, G1b 변조 주입 100% 차단, 정상 입력 통과, 수정 루프 종료 조건

### 3-8. 타임라인 담당 (Timeline Artist, P1)
- 페르소나: 사건 흐름을 한눈에 보이게 그리는 담당. 그림에는 글자를 넣지 않는다.
- 모델: `muse-image-1.0`
- 입력: 이벤트 종류와 순서(값 없이), 스타일 지침(가상 브랜드, SAMPLE 표시, 글자 없음)
- 처리: 글자 없는 삽화 생성 → G7(글자 없음) 통과 시 채택, 실패 시 1회 재생성, 다시 실패하면 SVG만 사용. 날짜와 금액은 코드가 SVG로 삽화 위에 얹습니다.
- 시연용 모드(선택): 그림에 숫자를 그리게 하고 G7이 기준값과 비교
- 테스트: G7 통과·실패 경로, SVG 대체 동작, 오버레이 값이 기준값과 일치

### 3-9. 편철 담당 (Packager, 규칙)
- 책임:
  - 값 슬롯을 사용자 확인값과 계산값으로, 인용 슬롯을 사용자가 확인한 판독 원문으로 치환
  - 청구취지 정형문, 청구원인의 시작·맺음 정형 문구, 당사자 표시, 사용자가 고른 제출 법원명 삽입
  - 내용증명 PDF, 전자소송 복사 블록(지급명령 청구취지·청구원인), 갑호증 통합 PDF와 증거설명서(이의신청 이후 소송 또는 소액사건 소장 대비용), (P1) SC-100 기입과 Demand letter
  - 서류에 `DISCLAIMER_KO`/`DISCLAIMER_EN` 표시
- 테스트: 남은 슬롯 0개, 인용 슬롯 원문 일치, 계획서 4-6절 PDF 테스트, G1b 통과

### 3-10. 접수 담당 (Intake, 규칙)
- 책임: SHA-256, 호증 번호(KR 갑 제N호증, US Exhibit A~), 파일 형식 확인, 원본 보관. 영상은 ffmpeg로 초당 2장을 뽑은 뒤 비슷한 프레임을 걸러 핵심 프레임만 남깁니다(판독 담당이 영상을 직접 받는 경우에도 스틸컷 후보로 사용).

### 3-11. 녹취 담당 (Transcriber, P2)
- 모델: `muse-voice-transcribe-1.0`
- 책임: 통화 녹음을 화자 구분 녹취록으로 만들고, 판독 결과와 같은 형식으로 사실 정리 담당에게 넘깁니다.

## 4. 공통 계약

### 4-1. 작업과 결과 형식

```python
class AgentTask(BaseModel):
    case_id: str
    agent: str
    inputs: dict          # CaseState 구역의 ID만 전달
    constraints: dict     # 예산, 언어, 재시도 횟수

class AuditRecord(BaseModel):
    model_id: str | None  # 규칙 담당이면 None
    prompt_version: str | None
    input_hashes: list[str]
    latency_ms: int
    tokens_in: int
    tokens_out: int
    cost_usd: float

class AgentResult(BaseModel):
    agent: str
    status: Literal["ok", "hold", "fail"]
    outputs: dict         # 담당별 스키마
    warnings: list[str]
    audit: AuditRecord
```

### 4-2. 사건 상태 (CaseState, 공유 칠판)
- 각 담당은 자기 구역에만 씁니다. 판독 담당은 `readings`, 사실 정리 담당은 `fact_candidates`, 사용자는 `confirmed_facts`, `highlight_selection`, `draft_approvals`에 씁니다.
- 구역: `evidence`, `readings`, `segments`, `redaction_plan`, `fact_candidates`, `confirmed_facts`(기준값), `highlight_selection`, `calculations`, `drafts`, `draft_approvals`, `gate_results`, `timeline`, `packages`, `privacy_checks`, `audit_log`, `state`
- 저장: 데모 범위에서는 사건별 JSON 파일. 쓸 때마다 버전을 올립니다. 사건 폴더는 git에 올리지 않습니다.

### 4-3. 상태 기계

```text
INTAKE → (READING ∥ VISION_1) → (ORGANIZING ∥ VISION_2) → PRIVACY_PLAN → CHECKPOINT_1
→ TRACKING(P1) → CALCULATING → DRAFTING ⇄ VERIFYING → DRAFT_APPROVAL
→ TIMELINE(P1) → PACKAGING → FINAL_CHECK → CHECKPOINT_2 → DONE
```

- HOLD로 가는 경우: G2 결손, G4 한도 초과, 스키마 2회 실패, 수정 루프 2회 초과, 예산 초과, 최종 검사에서 누출 발견
- HOLD 화면에는 이유와 사용자가 할 일을 함께 보여 줍니다(양식 칸 기준 문구).
- 병렬 단계의 결과는 `evidence_id` 순으로 정렬해 저장합니다(실행 순서와 무관하게 결과 고정).
- 얇은 흐름(M2)에서는 TRACKING, TIMELINE을 건너뛰고 VISION_1·2를 빈 결과로 둔 채 끝까지 돌립니다.

### 4-4. 프롬프트 관리
- 위치: `backend/app/agents/prompts/<agent>.v<N>.md`. 맨 위에 버전과 변경 이유를 적습니다.
- 공통 머리말: 역할, 금지 사항(법적 조언·평가 금지, 명칭 규칙), 출력 JSON 스키마, 불확실할 때의 처리
- 프롬프트를 바꾸면 버전을 올리고 L3 골든셋을 다시 돌립니다.

문안 작성 담당 프롬프트 머리말 예시:

```text
너는 ClaimBack-AI의 문안 작성 담당이다.
- 확인된 사실 슬롯, 인용 슬롯, 증거 태그만으로 사실 문장을 만든다.
- 숫자(아라비아 숫자, 한글 수사), 날짜, "다음 달" 같은 상대 날짜, 사람 이름·성·호칭을 직접 쓰지 않는다. 반드시 {{slot}}을 쓴다.
- 말풍선 원문을 인용할 때는 {{quote:EX번호:항목ID}}만 쓴다.
- 증거로 뒷받침되는 문장(type=fact)에는 [[EX:n]]를 1개 이상, 사용자 진술 문장(type=user)에는 [[USER]]를 붙인다.
- 청구취지, 시작·맺음 정형 문구는 쓰지 않는다.
- 법적 평가, 결과 예측, 조언을 쓰지 않는다. "채무를 인정했다"처럼 법적 성격을 붙이지 않는다.
- 출력은 SlotDraft JSON 스키마만 따른다.
```

| L4 | E2E에서 에이전트 보드 상태 전환과 체크포인트 | 통과 |

## 7. 비용·지연 영향
- 추가 호출: 사실 정리 1회, 문안 수정 최대 2회, G6 재판독(P1)은 최종 PDF 1회. 1회 실행 약 $0.4~0.7(추정).
- 판독과 감식-1을 병렬로 돌리고 파일 해시 기준으로 캐시합니다. 실행 시간 목표는 체크포인트 대기를 뺀 기계 시간 3분 이내(잠정, M0 측정 후 다시 정함).
- Meta Spend Limit은 알림만 보내므로 코디네이터의 예산 상한(실행당 $2, 누적 $20)이 유일한 차단 장치입니다(계획서 4-7).

## 부록 A. 개발 체계: Muse Code 구현, Claude 리뷰

v1의 "Claude Code 서브에이전트로 개발" 안은 v1.1에서 삭제했습니다. 구현과 검증은 Muse Code가 하고, Claude는 지시와 리뷰만 합니다. 절차는 계획서 4-3절입니다.

| 주체 | 맡는 일 | 산출물 |
|---|---|---|
| Claude | 작업 지시서 작성, specs 관리, 리뷰(테스트 재실행, diff, 렌더 확인) | `specs/tasks/M<N>-*.md`, `reports/M<N>-review.md` |
| Muse Code | 지시서대로 구현, 테스트 작성·실행, 실호출 테스트 | 코드, 테스트, `reports/M<N>.md` |
| 사용자 | 지시 전달(대화형 또는 Claude 헤드리스 실행 중 선택), 승인, 커밋 승인 | 승인 기록 |

- Muse Code는 루트 `AGENTS.md`를 프로젝트 지시 파일로 읽습니다(작업 폴더를 신뢰해야 로드). 구현 규칙과 금지 사항은 그 파일에 둡니다.
- Muse Code의 서브에이전트·워크플로 기능을 쓸지는 Muse Code 쪽에서 정하되, 지시서의 완료 기준과 리포트 형식은 그대로 지킵니다.
