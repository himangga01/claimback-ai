## 1. 총평

원안을 바로잡은 v2.1의 큰 방향은 맞습니다. Muse Wonder 대체, "법 우회" 표현 삭제, 사용자 확인값을 기준값으로 두는 구조, 숫자·이름을 슬롯으로만 넣는 구조, 소액재판 한도 수정이 그렇습니다. 남은 문제는 세 가지입니다.

1. **전제가 바뀌었습니다.** 계획서 4-1절은 Meta API가 막힌 클라우드 작업 환경을 전제로 GitHub Actions 우회 경로를 짰습니다. 지금 이 PC에서는 `api.meta.ai`에 바로 닿습니다. 마감도 1시간 이를 수 있습니다.
2. **문서 사이와 문서 안에 모순이 몇 군데 있습니다.** G1 정의, 판독·감식 병렬 실행, 금지 명칭과 고지 문구가 대표적입니다. 구현 전에 정리해야 테스트 기준이 흔들리지 않습니다.
3. **약 80시간에 비해 범위가 여전히 큽니다.** 담당 12개, 게이트 7개, 두 관할, 영상 추적, 3분할 UI에 에이전트 보드까지 있습니다. 화면은 M6(11/4 정오)에야 시작합니다. 얇게라도 끝까지 이어지는 흐름을 먼저 만들고 넓혀 가는 순서가 안전합니다.

### B. 설계 모순

#### B1 [상] G1의 정의가 두 문서에서 다름
- 계획서: "G1 수치·고유명사 일치" (생성 문장의 값을 기준값과 비교). 테스트는 "5,000,000 → 500,000 변조 100건 차단".
- 에이전트 설계: "G1 슬롯 무결성" (슬롯 밖 숫자·이름 검출). 문안 작성 담당은 숫자를 아예 쓰지 않습니다.
- 슬롯 구조에서는 초안에 틀린 금액이 들어갈 길이 "규칙 위반 리터럴"뿐이라, 두 정의가 서로 다른 것을 검사합니다.
- 조치: 두 단계로 나눕니다.
  - **G1a (초안 검사)**: 문안 작성 담당 출력에 슬롯 밖 리터럴(숫자, 날짜, 이름)이 있거나 없는 슬롯 이름이 있으면 거부.
  - **G1b (최종 서류 검사)**: 편철 후 PDF에서 텍스트를 뽑아 금액·날짜·이름이 기준값과 일치하는지 대조. 편철 버그를 잡습니다.
  - 데모의 "틀린 금액 차단" 장면은 G1a(초안에 "500만 원"을 직접 쓴 경우) 또는 G1b(서류 변조 주입)로 보여 줍니다.

#### B2 [상] "판독 ∥ 시각 감식" 병렬 실행과 의존 관계가 충돌
- 상태 기계는 `(READING ∥ VISION)`인데, 시각 감식 담당은 "판독 결과의 박스·명사구로 분할"합니다. 박스 프롬프트는 판독이 끝나야 생깁니다.
- 조치: 감식을 둘로 나눕니다.
  - VISION-1(명사구: signature, stamp, face, chat bubble)은 판독과 병렬.
  - VISION-2(판독 박스로 보정, 고른 말풍선 영상 추적)는 판독 이후.

#### B3 [중] 금지 명칭 검사와 고지 문구가 충돌
- 명칭 검사는 UI 문자열 전체에서 "변호사"가 0건이어야 한다고 하는데, 고지 문구 초안(계획서 6장)에 "변호사에게 받으세요"가 있습니다.
- 법이 막는 것은 자기를 변호사나 법률사무소로 **표시**하는 일이지 단어 자체가 아닙니다(변호사법 제112조 제3호 취지).
- 조치: 금지 대상을 "자기 지칭(에이전트 이름, 제품 설명, 서류 작성자 표시)"으로 좁히고, 고지·안내 문맥은 허용 목록(문구 ID 단위)으로 관리합니다. 테스트도 허용 목록 밖에서 0건으로 바꿉니다.

#### B4 [중] "채무 인정 말풍선 고르기"는 법적 성격 판단
- 계획서 1-2(5)에서 Spark가 "어떤 말풍선이 채무 인정인지 고르"게 되어 있습니다. 채무 승인은 시효 중단 효과가 있는 법률 개념이라, 스스로 정한 "법적 평가 금지" 원칙과 부딪힙니다.
- 조치: Spark는 사실 분류만 합니다(예: 빌려 달라는 요청, 금액 언급, 갚겠다는 약속과 날짜). 서류에 강조할 말풍선은 사용자가 고릅니다. UI 문구도 "상환 약속 발화"처럼 사실을 묘사합니다.

#### B5 [하] 아키텍처 그림의 순서
- 계획서 2장 그림은 [5] 게이트를 [6] 초안보다 앞에 둡니다. 실제로 G1·G3은 초안 뒤, G7은 타임라인 뒤, G6은 편철 뒤에 돕니다. 에이전트 설계 4-3절의 상태 기계 순서로 그림을 맞춥니다.

#### B6 [하] 범위 표와 데모 대본의 불일치
- 데모 마무리 "Meta 모델 4종 사용"의 4번째는 P2인 Voice Transcribe입니다. P2를 빼면 3종이 됩니다(Spark, SAM 3.1, Muse Image).
- P0에 "청구원인 초안(한·영)"이 있지만 미국 서류는 P1입니다. 영어 초안은 P1로 옮깁니다.
- v2.1에서 추가된 에이전트 보드의 우선순위가 범위 표에 없습니다. 데모 핵심 화면이므로 P0로 적되, 처음에는 단계 목록과 상태 표시만 만드는 얇은 버전을 권합니다.
- 디렉터리 루트 이름이 `claimback-ai/`인데 실제 폴더는 `claimback-ai-meta`입니다.

### C. 도메인 정확성

#### C1 [상] 한국 이자 계산 테스트 케이스를 다시 정의
계획서 4-4절의 케이스는 "구간별(연 5%, 송달 다음 날부터 연 12%) 금액이 원 단위까지 일치"를 요구합니다. 그런데 송달일은 신청 시점에 알 수 없으므로 12% 구간 금액은 정할 수 없습니다. 계산 담당이 청구취지를 위해 실제로 내야 하는 값은 **충당 후 남은 원금과 지연손해금 기산일**입니다.

같은 조건(원금 5,000,000원, 변제기 2026-04-10, 이자 약정 없음, 2026-05-01 1,000,000원 변제)으로 계산하면 다음과 같습니다.

| 단계 | 값 |
|---|---|
| 지연손해금 기간 | 2026-04-11 ~ 2026-05-01, 21일 (변제기 다음 날부터, 변제일 포함) |
| 지연손해금 | 5,000,000 × 5% × 21/365 = 14,383.56 → **14,383원** (원 미만 버림 가정) |
| 충당 (비용 → 이자 → 원본) | 지연손해금 14,383원, 원본 985,617원 |
| 남은 원금 | **4,014,383원** |
| 청구취지 | "채무자는 채권자에게 4,014,383원 및 이에 대하여 2026. 5. 2.부터 이 사건 지급명령 정본 송달일까지는 연 5%, 그 다음 날부터 다 갚는 날까지는 연 12%의 각 비율로 계산한 돈을 지급하라." |

- 조치:
  - 고정 테스트의 기대값을 위 표로 바꿉니다. 화면에 보여 줄 "예상 총액"은 가정한 기준일을 함께 표시하는 참고값으로만 둡니다.
  - 정해야 할 규칙: 원 미만 처리(버림 권장), 변제일 당일 포함 여부, 윤년 일수(365 고정 또는 366), 이자 약정이 있는 경우 지연손해금 이율(민법 제397조), 상사채권 판정은 사용자 선택값.
  - 위 계산 규칙의 법적 근거는 이 세션에서 법령 원문으로 다시 확인하지 않았습니다(일반 지식 기준). 구현 전에 근거 조문을 `specs/`에 적어 둡니다.

#### C2 [중] 지급명령과 갑호증의 관계
- 지급명령은 채무자를 심문하지 않고 서면으로 발령하는 절차라, 신청에 증거 첨부가 필수가 아닌 것으로 알고 있습니다(확인 필요). 갑호증 통합 PDF와 증거설명서는 채무자가 이의신청해 소송으로 넘어가거나 처음부터 소액사건 소장을 낼 때 쓰입니다.
- 조치: 데모와 README에서 "지급명령 신청 문구 + 이의신청 이후를 대비한 증거 묶음"으로 설명합니다. 지급명령 신청에 갑호증이 꼭 필요한 것처럼 보이지 않게 합니다.

#### C3 [중] G4가 금액만 보고 관할 법원은 보지 않음
- 한국 지급명령은 채무자 주소지 등 정해진 법원에 신청해야 하고(민사소송법 제463조, 확인 필요), SC-100에도 관할 법원을 고른 이유를 적는 칸이 있습니다.
- 조치: 법원을 판정하지 말고 "채무자 주소" 입력칸과 법원 찾기 안내 링크만 둡니다. 사용자가 고른 법원명을 슬롯으로 넣습니다.

#### C4 [중] 미국 트랙에 한국어 증거를 쓰는 문제
- 캘리포니아 법원에 한국어 대화 캡처를 내면 영어 번역이 필요할 가능성이 큽니다(확인 필요).

#### C5 [하] G2 보류 문구
- "청구 요건 미충족"은 법적 판단처럼 들립니다. "이 양식의 다음 칸을 채울 근거가 없습니다: 이체 내역, 갚기로 한 날짜"처럼 양식 칸 기준으로 씁니다.

### D. 생성·검증 구조

#### D1 [상] 슬롯 검사가 잡아야 할 범위가 숫자 정규식보다 넓음
- 한국어 문장에는 숫자를 피해 가는 표현이 많습니다: 한글 수사("오백만 원", "5백만원", "삼십일"), 상대 날짜("다음 달", "지난주 금요일", "열흘 뒤"), 부분 이름·호칭("김 씨", "철수야", 성만 쓰기).
- 청구원인에는 말풍선 원문 인용("다음 달까지 꼭 갚을게")이 자주 들어가는데, 이 문장에는 상대 날짜가 들어 있습니다.
- 조치:
  - G1a 검사 목록에 한글 수사, 상대 날짜 표현, 기준값 이름의 부분 일치(성, 이름, 호칭)를 넣고 변조 주입 테스트에도 같은 유형을 넣습니다.
  - 원문 인용은 `{{quote:EX1:item3}}`처럼 판독 항목을 가리키는 인용 슬롯으로만 넣고, 편철 담당이 사용자가 확인한 원문으로 바꿉니다.

#### D2 [중] "문장마다 증거 인용"을 문장 유형별로
- "채무자는 현재까지 갚지 않고 있습니다" 같은 미변제 사실은 증거가 아니라 부재로 뒷받침됩니다. 모든 문장에 인용을 강제하면 억지 인용이 생깁니다.
- 조치: 문장 유형을 나눕니다. 사실 문장은 `[[EX:n]]` 필수, 사용자 진술 문장은 `[[USER]]` 태그, 정형 문구(시작·맺음)는 편철 담당이 틀에서 넣고 문안 작성 담당은 쓰지 않습니다.

#### D3 [중] Muse Image에 숫자를 그리게 하지 않기
- 이미지 생성 모델은 그림 속 글자를 자주 틀리므로 G7 실패, SVG 대체가 오히려 기본 경로가 될 가능성이 큽니다.
- 제안: Muse Image는 **글자 없는 삽화**(인물, 돈, 달력 같은 장면)만 그리고, 날짜·금액은 코드가 SVG로 위에 얹습니다. G7은 "그림에 글자나 숫자가 없는지"를 Spark로 확인하는 쉬운 검사가 됩니다. "AI가 그린 것을 검증한다" 장면을 살리고 싶으면 지금 설계를 시연용으로 남겨 둘 수 있습니다.

#### D4 [중] 법적 위험이 가장 큰 지점은 AI가 쓰는 청구원인 문장
- 1-1(2)의 근거는 "사용자가 쓴 내용을 양식에 기계적으로 넣는 자동화"입니다. 문안 작성 담당이 reasoning high로 문장을 지어 쓰는 부분이 이 설명에서 가장 멉니다.
- 선택지: (가) 사건 유형별 고정 문장 틀(대여, 교부, 변제기 약정, 일부 변제, 독촉)을 기본으로 하고 AI는 사건 순서 배열과 연결 표현만 맡김, (나) 지금 설계 유지 + 문장별 사용자 수정·승인 UI. 해커톤 범위에서는 (나)도 무리가 없지만 공개 배포 전에는 변호사 검토에서 이 부분을 꼭 묻습니다.
